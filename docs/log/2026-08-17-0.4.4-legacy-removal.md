## 적대검증 루프 실측

1차 critic 불통과(높음2·중간3·낮음8) — 코드 자체는 견고(우회 경로 변형 36종 probe 전부 차단·뮤테이션 10종 사멸)했지만 **게이트가 구조적으로 못 잡는 지점**을 잡음:
- **deploy 명령이 실제로 깨져 있었음** — 편승 L11의 `npm ci`가 pnpm 워크스페이스 락과 비동기화로 EUSAGE. "설정 한 줄" 편승도 실행 검증 필수.
- **핵심 계약(레거시 읽기 0)에 회귀 그물 부재** — fallback 재삽입 뮤테이션 2종이 189개 테스트에서 생존. 상태코드 단언은 assertOwner가 대신 막아줘서 무력 → **R2 조회 키 전수가 `private-v2/` 접두인지 단언**이 실질 방어선(재검증에서 사멸 확인).
- 반쪽 상태의 나머지 절반: D1 레거시 행(유령 행·익명 행 삭제 불가) — 런북 D2에 D1 실측·정리 추가.

## 교훈

1. **뮤테이션 테스트가 게이트의 사각을 드러낸다** — 195 green이어도 핵심 보안 계약의 회귀 그물은 별개 문제. "이 코드를 되살리면 어떤 테스트가 죽나"를 물어야 한다.
2. **보안 계약 테스트는 결과(상태코드)가 아니라 행위(조회 키)를 단언하라** — 다른 방어선이 대신 막아주면 결과 단언은 통과해버린다.
3. 편승 항목도 실행 검증 — 문법상 유효한 설정 한 줄(`npm ci`)이 락 비동기화로 실행 불능이었다.
4. plan-audit 3회차(특히 타사 AI 교차)가 계획 단계에서 잡은 것(pack.ts fallback 짝 제거·순서 의존·테스트 수치)은 구현 단계였다면 재작업 비용이 몇 배였다.
